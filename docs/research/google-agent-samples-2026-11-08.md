### A.3 The Claude extension template (G/agents-cli/extensions/claude/template)

`app/agent.py` builds a `claude_agent_sdk.ClaudeAgentOptions` named `root_agent` with one SDK-MCP tool `get_weather({"city": str})`, `tools=[]` (no Claude Code built-ins), `allowed_tools=["mcp__weather__get_weather"]`, `max_turns=10`. `references/claude.md` says each turn runs in a Claude Code CLI subprocess on Vertex (`CLAUDE_CODE_USE_VERTEX=1`), denies tools outside `allowed_tools` (`permission_mode="dontAsk"`), and that on Agent Runtime `publish gemini` is refused and Console sessions/traces stay empty (same degradation agents-cli documents for LangChain). Its eval dataset (`tests/eval/datasets/basic-dataset.json`) has two cases, `greeting` and `weather_lookup`, authored as user events. This is the closest Google artefact to our `claude_managed` target, and it also evaluates only final-response quality.

### A.4 How Google's LangChain extension produces traces (important for D)

`G/agents-cli/extensions/langchain/template/scripts/eval_generate.py` (`generate_traces`) runs `root_agent.invoke({"messages": [...]})` per user turn and appends **only** `{"author": <agent>, "content": {"role": "model", "parts": [{"text": reply}]}}`. It never emits `function_call` / `function_response` parts, so a LangChain agent graded through agents-cli has no tool trajectory for `multi_turn_tool_use_quality` to see. It does set `turn_index`, `turn_id="turn_<i>"` on every turn and appends `responses=[{"response": Content}]` with the final reply, with the comment that the Eval Service rejects traces without `turn_index` and "scores nothing because the response candidate is empty" without `responses`. The built-in ADK generator (`G/agents-cli/src/google/agents/cli/eval/cmd_generate.py` `merge_events_into_case`, `_events.py` `parse_content_event`) keeps function_call/function_response parts and `state_delta` from ADK `/run_sse` events, and `split_case_history` seeds prior turns (the "N+1" continuation shape) as history, answering only the trailing user event.

## C. Edge-case catalogue

| Synthesised scenarios | `eval dataset synthesize` → `user_scenario{starting_prompt, conversation_plan}` (ADK only) | — | **no** |
| Analysis | `eval compare`, `eval analyze` (failure clustering), `eval optimize` (GEPA) | — | `mfa compare` |

### D.2 What `mfa export -t gemini_eval` (R/src/mfa/evals/export.py) cannot express yet, measured against what Google's own generators emit

1. **`responses`**: Google's generators always append `responses=[{"response": Content}]` with the final reply (G/agents-cli/extensions/langchain/template/scripts/eval_generate.py `generate_traces`: "scores nothing because the response candidate is empty"; cmd_generate.py `merge_events_into_case`). Our export puts the reply only as the last `events[]` item. The single-turn built-ins (`final_response_quality`, `hallucination`, `safety`) read `responses`; add it.
2. **`turn_id`**: the LangChain generator sets `turn_id=f"turn_{i}"` next to `turn_index`; ours sets only `turn_index`.
3. **`prompt`**: single-turn cases from `prompt` keep that field in Google's output; ours always emits `agent_data`, which makes every case "multi-turn" for the single-turn-only metrics (dataset_schema.md: "Single-turn metric ... received agent_eval_data with N turns").
4. **`reference` / `context` / `rubric_groups`**: not in our YAML, so not exported; our `judge` is exported as a non-standard top-level `rubric` string. A list-valued `judge` could map to `rubric_groups.{mfa}.rubrics[]` so the managed rubric metric can grade it.
5. **Tool errors**: `function_response.response` carries the error text as `{"result": "Error: ..."}` with no error flag; Google's traces have no flag either, but the Eval Service's `hallucination` and tool-use rubrics read the response body, so the current mapping is acceptable; recording `is_error` on `ToolCall` would let us emit `{"error": ...}` consistently.
6. **`state_delta`** events and `session_input.state`: nothing to export until the template has tool state (#9).
7. **Author of `function_response`**: ours uses `"tool"`, Google's example uses the agent id (dataset_schema.md); both are legal ("user", agent_id, or "tool").
8. **Model-internal tools**: n/a for us, an advantage (our function tools are always visible, so `multi_turn_tool_use_quality` can grade every target, including CMA).
9. **ADK `.evalset.json` export**: not supported at all. The shape is simple (`conversation[].user_content`, `final_response`, `intermediate_data.tool_uses[{name,args}]`, `session_input`), and it is what `adk eval` and the starter-pack's `make eval` consume, so a second exporter would let `tool_trajectory_avg_score` / `response_match_score` grade our runs too.

## E. Recommended next example agents

Design rules shared by all three (each is something a Google sample actually does): tools are plain `@tool` functions with typed, docstring'd arguments (so the schema is derived once, R/src/mfa/spec.py); every tool has a `fixture` provider behind an env toggle like `MFA_WEATHER_PROVIDER` (Google: `INTEGRATION_TEST=TRUE`, `USE_MOCK_API`); tools return references, never bytes (Google: retail-virtual-tryon, genmedia); "not found" and "rejected" are **results with alternatives**, not exceptions (Google: staged-ui-widgets `status: not_found|rejected` + `editable_fields`/`available`); approval is a conversational step the model must take before calling the mutating tool (Google: deep-search planner, brand-aligned `requires_approval`). Fields marked *(proposed)* are from section C; everything else uses today's YAML.

### E.2 `docs_research_agent` (grounded Q&A with citations over a fixture corpus) — modelled on core/python/deep-search, rag-vector-search, contrib/python/llm-auditor, high-volume-document-analyzer

Domain: answers questions about a bundled corpus (`agents/docs_research_agent/corpus/*.md`, ~15 short internal docs plus one deliberately huge one) with inline citations, iterating search → read → answer with a bounded number of rounds.

Tools:
1. `search_docs(query: str, top_k: int = 5) -> dict` → `{hits: [{doc_id, title, snippet, score}]}` (deterministic BM25-style scoring over the fixture; the portable stand-in for `google_search` / `VertexAiSearchTool`).
